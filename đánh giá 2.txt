1. Tóm tắt điều hành
Hệ thống đã triển khai đúng 69/90 thực thể ERD (77%) với chất lượng cao ở lõi nghiệp vụ (Auth, RBAC 3 tầng, Issue/Workflow FSM, Sprint/Board, Custom Field). Tuy nhiên có 3 lớp vấn đề kết nối khiến nhiều tính năng "trông như có" trên UI/API nhưng không thực sự vận hành đúng vòng đời dữ liệu mô tả trong SRS:

Đứt gãy chuỗi sự kiện (event chain). outbox_events — trục xương sống event-driven theo SRS §3.3/§14.2 — hiện chỉ có một nhánh tiêu thụ (tạo notification in-app cho issue). Hai nhánh còn lại (Webhook, Automation) có đầy đủ CRUD, ký HMAC, chặn SSRF, nhưng không bao giờ được kích hoạt bởi sự kiện thật — đây là "kết nối giả" (module tồn tại độc lập, không nằm trong luồng dữ liệu chính).
Thiếu 13/13 thực thể "Configuration Schemes" — đúng 0% domain này được triển khai. Hệ quả dây chuyền: issues.priority là chuỗi tự do thay vì FK, issues.resolution_id là cột mồ côi không FK, không có tầng "issue-type/priority theo project" như SRS mô tả, phá vỡ giả định BR-42..44 của chính SRS.
Không có API cấu hình Workflow (state/transition) sau khi tạo project — toàn bộ 90 entity ERD giả định workflow là cấu hình được (workflows/workflow_states/workflow_transitions + workflow_schemes), nhưng thực tế mỗi project chỉ có đúng 2 state cứng sinh tự động lúc tạo. Đây là khoảng cách lớn nhất giữa "ERD hứa hẹn" và "code thực thi".
Các phần lõi được nối đúng chuẩn và nên giữ nguyên làm baseline: RBAC resolver (org role → permission; project role/group role → permission scheme), Issue transition → State History → Activity Log → Outbox (transactional), Sprint ↔ issue_sprint_history ↔ issues.sprint_id cache, Board ↔ workflow_state qua board_column_states, Issue Security access-check ở tầng đọc.

0.1. Tạo OutboxDispatcherService (thay thế dần logic trong OutboxService.publishPending()):

// Method signature đề xuất
async dispatch(manager: EntityManager, event: OutboxEvent): Promise<void> {
  await this.notifyInApp(manager, event);        // giữ logic hiện có
  await this.dispatchWebhooks(manager, event);    // MỚI
  await this.triggerAutomations(manager, event);  // MỚI
  await this.enqueueEmailDeliveries(manager, event); // MỚI — dùng notification_preferences
}

dispatchWebhooks(event): SELECT * FROM webhook_subscriptions WHERE org_id=:orgId AND status='active' AND events @> [:eventType] AND (project_id IS NULL OR project_id=:projectId) → với mỗi dòng gọi WebhookService.enqueue(subscriptionId, event.id) (hàm đã có sẵn, chỉ cần gọi nó).
triggerAutomations(event): SELECT rules WHERE status='active' AND EXISTS (component trigger có component_key khớp eventType) → gọi AutomationService.executeFromEvent(rule.id, event) — hàm mới, khác execute() cũ ở chỗ thực sự chạy action: đọc cây automation_rule_components, với mỗi node action gọi đúng command service tương ứng (IssueService.transition, IssueService.update, IssueService.addComment...) — không tự viết SQL trực tiếp, tái dùng toàn bộ validation/permission đã có trong các service đó.
enqueueEmailDeliveries(event): với mỗi recipient trong notifyInApp, kiểm notification_preferences.channel='email' AND enabled=true → nếu có, gọi MailService.send() rồi manager.save(NotificationDelivery, {...}).

0.3. Worker gửi Webhook thật:

Thêm WebhookDispatcherWorker (interval riêng, ví dụ 10s): đọc webhook_deliveries WHERE status='pending' AND next_attempt_at<=NOW(), gọi fetch(url, {method:'POST', headers:{'X-Signature': sign(...)}, body}), cập nhật attempts/responseStatus/nextAttemptAt (backoff luỹ thừa: 30s, 2m, 10m, rồi failed).
Definition of Done (DoD) Giai đoạn 0:

[ ] Tạo issue → có webhook subscription khớp event → thấy webhook_deliveries.status='success' với response_status=2xx trong vòng 15s.
[ ] Automation rule "issue chuyển Done → gán label 'released'" → issue chuyển Done thật → label được gán tự động, có automation_executions.status='completed' với resultJson.actions >= 1.
[ ] Bật notification_preferences(channel='email', enabled=true) → nhận được email thật (hoặc log SMTP giả lập), có dòng notification_deliveries tương ứng.
[ ] Retry outbox event 2 lần liên tiếp (giả lập lỗi) → không nhân đôi webhook delivery / automation execution (test theo idempotency key có sẵn).

→ Backend đã có API custom field theo context (CustomFieldController.projectContexts) nhưng frontend create-issue không gọi, nghĩa là dù Org Admin định nghĩa custom field bắt buộc (isRequired=true), người tạo issue trên UI không hề thấy field đó → vi phạm trực tiếp mục tiêu "required field phải được enforce ở cả client lẫn server" (FR-CONF-02), vì phía client hoàn toàn vắng mặt.
